# ARM64 对象更新分解与组件 getter 三路径实测（2026-10-31）

在既有 Fusion ARM64 Ubuntu guest 上继续真实 libg warm-step 优化，固定 2 vCPU / 6144 MiB、
引擎、资源、两种八卡组、seed 1/7 和非空固定动作。本阶段没有并发测试、系统配置变更或
外围 Android 服务重建。整体 warm-step、硬件计数和长期稳定性目标继续进行。

## 结论与决策

- 对象集合临时 new[]/delete[] 在四组诊断中的累计耗时仅占对象窗口 0.71%–0.94%。
  本轮不引入缓冲池；组件更新占 73.66%–76.94%，后续仍沿组件实际调用链定位。
- 新 component-getters-v1 包含旧 11 点和新增 41 点，共 52 点，保持默认关闭。
  相对原始路径四组批次中位耗时下降 3.75%–5.79%，但大部分来自旧候选。
- **相对旧 11 点的增量不一致**：四组耗时变化 -0.57%、+0.75%、+0.45%、-1.01%；
  六个配对 block 分别 4/2/2/5 个更快。没有跨 fixture 稳定增量收益结论，不提升为默认。
- 16 个完整局与历史原始路径的全部 serializer 帧及已观测状态一致；这是所覆盖输入的
  局部正确性门，不是全部内部状态、卡牌、玩法或异常执行语义的证明。

## 候选实现与边界

新增调用者范围为 +0xf6594c..+0xf65cc8 和 +0xf65cc8..+0xf666d0，最后地址为开区间。
逐点将 BL 替换为原 getter 的单条 LDR，原 getter 正文均为同宽、同偏移 LDR + RET；
不缓存、不提前读取、不重排。全部原 BL、getter 正文及调用者入口精确核对后才修改。
审计完整调用者的 LR 保存/恢复、return 和尾跳；正常执行语义保持，signal/fault PC、
profiler 栈和异步观察不承诺相同。原始库文件保持原样，安装只作用于一次性进程。
代码页 RW→RX 并刷新指令缓存，重复 reset 不重复安装，跨候选切换拒绝。

旧 hot-getters-v1 仍只安装 11 点；新 52 点候选包含它，不是同时叠加两个开关。
空间候选及 native 诊断仍互斥。诊断 observer 与 benchmark observer 独立，不将其绝对
耗时相互比较。完整审计保存在私有证据，公开只含自有实现、地址、摘要和哈希。

## 平衡串行三路径 benchmark

同一 observer，a=原始、b=旧 11 点、c=新 52 点。每 case 六个 block，顺序依次为
abc / bca / cab / cba / acb / bac，每 variant 在三个位置各出现两次。
72 批、8352 局全部正常完成；每批 16 局 warmup + 100 测量，共 7200 测量局。
每 16 tick 采样，reset 间轮转起始相位；正式计时关闭诊断、Frida、REA、Ghidra、
strace、逐 tick 快照和详细状态输出。冷启动、reset、资源加载和终态校验不计入 step-loop。

主机独立汇总器检查 72 批完整顺序、精确 command/env、输入 SHA、2 CPU/affinity、
安装标记、退出和每批 116 次原生终局，并从 raw stdout 重算全部保存及 controller 摘要。
正确性原始局终态 digest 按归档真实末帧字节重新计算，作为 benchmark 的固定终态身份。
benchmark 自身只验证终态，不能替代独立的全帧正确性门。
