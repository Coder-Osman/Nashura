# 事件驱动策略：架构、采集与后续自博弈

> 本文只讲三件事：**事件驱动的模型架构（重点是与原定步 V4 的区别：新增延迟头）**、**"采集"到底是什么以及速度多少**、**后面还没做的自博弈训练为什么瓶颈在引擎推进**。预训练部分很简单，跳过。
>
> 相关文档：`EVENT_DRIVEN_SPEC.md`（v1 草案，设计初衷）、`SEGMENT_REWARD_SPEC.md`（分段奖励设计）。

---

## 1. 一句话总览

原来的 V4 策略是"**每个 tick 都决策一次**"的定步策略。事件驱动版本把决策点改成"**每一次公开出牌事件**"：谁在什么时候出了什么牌，就是一次决策机会。因为两次事件之间隔多久是不固定的，模型除了"出哪张牌、放哪一格"，还必须回答"**隔多久再出**"——这就是新增的**延迟头**。

---

## 2. 事件驱动契约

| 项 | 约定 |
| --- | --- |
| 决策点 | 每一次公开出牌事件（事件级半马尔可夫，不是定步网格） |
| 观测时刻 | `play_tick + 1`：部署实体与 deployment ring 要到下一 tick 才可见（这条不变量在采集侧实测全部成立） |
| 动作 | 下张**己方卡**（deck 身份，不是 candidate 槽位）+ **100ms 量化的延迟** + 18×32 落点格 |
| 放弃动作 | 显式 **WAIT**：6 秒内没有下一次己方出牌就判 WAIT——因为更新的公开事件会取消这个计划 |
| 延迟词表 | 0–6000ms、步长 100ms，共 **61 个 bin**（视界 6000ms/50ms = 120 tick） |
| 被中断 | 计划执行前若出现新的公开事件，该计划作废 |

WAIT 这一支是事件驱动特有的：定步策略每个 tick 总要吐一个动作，而事件驱动允许"这个事件我不接"。

---

## 3. 模型架构

**编码器完全沿用 V4**（卡牌/塔/实体/编组/关系边/作用域/空间平面等共 139 个观测张量字段），这部分不变，本文不展开。变化全在**决策头**上。模型规模 **13.64M 参数**（52MB checkpoint），输出四个头：

### 3.1 gate 头（ACT / WAIT）
二分类。事件驱动必须显式回答"要不要接这个事件"，它决定了后续动作头是否参与监督（见 3.5 的 `act_mask`）。

### 3.2 卡牌头（pointer over deck）
不是在"4 张手牌"上做四选一，而是在**整副 8 张牌组**上做 pointer 打分：

```
card_logits = einsum("bd,bcd->bc", card_query(policy_context), own_card_memory) / sqrt(card_dim)
```

- 行数 `max_own_cards = 8`，按牌组顺序（`sorted(deck, key=vocab_id)`）。
- `own_cards.mask` 全为 True（含义是"槽位有效"，不是"在手牌里"）；**"是否在手牌里"只以特征形式存在**：`CARD_RUNTIME_FEATURE_NAMES[0] = in_hand`、`[1] = is_next_card`（每张卡 18 维运行时特征）。
- 标签对齐：`card_row` = 标签卡号在 8 行里的行号，找不到则 -1。

### 3.3 落点头（FiLM 调制的空间 pointer）
在 18×32 网格上打分，条件由 `policy_context` + **被选中那张牌的 memory 行**共同给出（`cell_condition` → `gamma/beta` → FiLM 调制空间记忆）：

```
cell_logits = einsum("bd,bdhw->bhw", cell_query(cond), keys(conditioned)) / sqrt(d)
```

### 3.4 延迟头（**本次新增**）
预测"从观测时刻到下一次己方出牌"的**时间**，61 类的分类头：

```
selected = _selected_card_memory(own_card_memory, card_row)      # 取被选中牌的 memory 行
delay_logits = delay_head(cat(policy_context, selected))
```

- **条件化在"将要出的那张牌"上**：延迟不是独立于牌的先验，而是"出这张牌会等多久"。
- 行号为 -1（WAIT）时，用可学习的 `wait_embedding` 顶替被选中的牌行，保证前向永远有定义。
- 训练用三项叠加：
  1. 主损失：61 类交叉熵；
  2. **邻域平滑**：标签 one-hot 向左右各摊一份（`--delay-neighbor-weight`，默认 0.1），因为 100ms 相邻 bin 语义几乎等价，不该被判为完全错误；
  3. **粗粒度辅助**：把 5 个细 bin 归一组做 logsumexp 得到粗分布再算 CE（`--delay-coarse-group 5`，权重 `--delay-coarse-weight 0.3`），给"大概多久"一个更稳的梯度。
- 优化上给延迟头参数单独放大学习率：`--delay-lr-mult 2.0`（AdamW 参数组）。
- 评价口径：`delay_exact`、`delay_within1`、`delay_within3`、`delay_coarse_acc`。

### 3.5 损失与掩码

```
act_mask = (gate == 1) & (card_row >= 0)
```

卡头 / 延迟头 / 落点头**只在 `act_mask` 为真的帧上计算**，gate 头在所有帧上算。也就是说：**标签必须能在观测里对得上，才产生动作梯度**。

> 这条掩码曾经造成过一个严重后果：早期缓存里 owner=1 的记录标签来自对手（`label_cache` 只按 `event_tick` 作键的 bug），对不上自己牌组，于是**约 44% 的 ACT 帧被静默排除**，报出来的 card_top1 其实只反映 owner=0 那一半。该问题已通过离线重算标签修复（owner=1 的 `label∈own_deck` 从 0.17 → 1.0000），现在两半都有效。

## 4. 与原定步 V4 的区别（速查）

| 维度 | 原 V4（定步） | 事件驱动（本版） |
| --- | --- | --- |
| 决策时机 | 每个 tick | 每次公开出牌事件 |
| 时间语义 | 隐含在 tick 里 | **显式由延迟头预测**（61 bin / 100ms） |
| 动作空间 | 直接出牌/放弃 | 出牌 + **延迟** + 落点，另有显式 WAIT gate |
| 卡牌目标 | native 手牌槽 / candidate | **牌组身份行**（8 行 pointer） |
| 头数 | 卡 / 格（+价值等） | **gate / 卡 / 延迟 / 格** 四个 |
| 训练数据 | 定步 rollout | 事件观测分片（`.crev.zst`） |
| 关键新增 | — | ① 延迟头（邻域平滑 + 粗粒度辅助 + 独立 LR）② WAIT gate ③ 事件边界对齐（观测 tick = play_tick + 1） |

一句话：**编码器没变，变化在"什么时候决策"和"多了一个预测何时动手的头"**。

## 5. 采集是什么

这里的"采集"**不是**人去打游戏，而是：**把归档的人类对局（replay）过一遍引擎，逐事件导出语义观测 + 专家动作标签**。

### 5.1 流程

1. 输入：RoyaleAPI 归档 replay（`IL_full`，**52 个 parquet part、252,238 局**；每条记录含 `payload_json`，里面是公开动作轨迹：`side` / `replay_tick_20hz` / `card_key` / `coordinates.grid_cell_floor` 等）。
2. 用原生引擎（游戏自身的 AArch64 库，跑在 AVD 里）**重演**这局，落在每个已记录的命令 tick 上。
3. 在每个"公开出牌事件"的下一个 tick（`play_tick + 1`）**张量化该 owner 视角的语义观测**，并配上下一步专家标签（卡 / 落点 / 100ms 量化延迟 / 或 WAIT）。
4. 一局写一个分片：`<shard_id>.crev.zst`（zstd 压缩的 safetensors 容器）+ `<shard_id>.json`（summary：`frames` / `act_frames` / `legal_act_frames` / `replays` / 校验和）。

### 5.2 组织形式

- 分片命名 `part-{pi:02d}-shard-{source_index:06d}`，分区规则是**跨步取模** `source_index % partition_count == partition_index`，三台机器各跑一个分区。
- 两个重要的工程约束：
  - **两条推进路径不完全等价**：默认的 Python checkpoint 步进 vs `--step-until-event`（原生事件步进）。后者快 1.54×，但两者产出的观测张量在 20/89 组上不同，**禁止混入同一缓存**。
  - **分片里不记录步进模式**，一致性只能靠纪律。
- 规模：**230,824 片 / 36GB**，覆盖归档的 **91.5%**（其余约 2–3% 是引擎侧永久失败的发牌校准局，外加部分尾部缺失）。
- 每局的数据量：典型分片约 150 帧（每帧 139 个观测字段）；一个 trigger event 会产出 owner 0/1 两条记录（两个视角各一条），所以"一局用两次"。

### 5.3 速度（实测）

| 环节 | 实测数字 |
| --- | --- |
| 引擎重演一局 | **约 32 秒 / 局 / 引擎**（单机 24 引擎 ≈ 0.75 局/秒） |
| 全量 252,238 局 | 三机 36 引擎并行 **约 2–3 天** |
| 训练侧消费 | 16 卡 DDP 约 **61 分片/秒**，全池一遍约 **1 小时** |
| 离线标签重算（纯 CPU，不用引擎） | 单机 6 进程 ~10.8 片/秒；改成每进程单线程后单机 ~16 片/秒，三机 30 进程修完 230,824 片约 **1 小时** |

> "采集"的机器成本几乎全在**引擎重演**这一步（CPU 侧的模拟推进），不在 GPU。

## 7. 后续的自博弈训练：瓶颈在引擎推进（尚未开始准备）

### 7.1 目标

把当前只能模仿人类（BC/IL）的策略，变成靠自博弈（PPO 类）持续改进的策略。V4 定步线上已有可用的自博弈设施（resident 多对局 + 三专精联盟），但**事件驱动的 rollout 循环还没有搭**。

### 7.2 为什么瓶颈是"引擎推进"

定步自博弈里，一个 batch 的动作可以在**一次引擎调用**里推进固定数量的 tick；事件驱动不一样，它的决策点是**稀疏且位置未知**的：你不知道下一个出牌事件在哪一 tick，只能持续推进引擎、逐 tick 检测事件，直到命中。

具体地，每产生**一个决策样本**需要：

1. **推进引擎直到下一个事件**：tick 数不定（快则相邻 tick，慢则几秒的空白期），这段推进是纯引擎时间；
2. 张量化观测（事件观测张量，139 字段）；
3. 策略前向 → 得到 gate / 卡 / **延迟** / 落点；
4. **按延迟头排程**：这是事件驱动独有的结构成本——动作不是"立刻执行"，而是要**预约到未来某个 tick**；期间引擎必须继续推进，同时监控是否出现**更新的公开事件**（出现则取消该计划）；
5. 执行/放弃 → 回到 1。

也就是说：**样本产出速率被"引擎每秒能推进多少 tick"钉住**，而不是 GPU。这与定步线上量到的画像一致——每个 round 的分解约 **tensorize 60ms + forward 78ms + decode 9ms + 引擎/通道 ~290ms**，引擎那一项占大头，GPU 利用率长期只有 **5–22%**。事件驱动只会更偏向引擎侧，因为每个样本还多了"推进到未知事件 + 延迟排程期间的监控"。

补充一个真实案例：纯 CPU 的离线标签重算（不用引擎，只解压/改标签/重压）在单机 6 进程时约 10.8 片/秒；这与自博弈无关，但说明**只要离开引擎，吞吐立刻上一个量级**——反过来印证了引擎推进才是那条链上的窄口。

### 7.3 缓解方向（按性价比）

- **原生事件步进**：`--step-until-event` 比默认 Python 步进快 **1.54×**（代价是观测张量不等价，所以必须与训练用的缓存同源，不能混）。
- **每引擎多对局**：resident 多对局把"一局一进程"改成"一引擎 8 槽并发"，聚合吞吐提到 ~2,190 tps（旧架构的 4.5×）。
- **把策略前向移出关键路径**：推进引擎与策略前向重叠（异步/预取），让 GPU 在引擎推进时也有活干，否则 GPU 就是空转等引擎。
- **批量化排程**：把"预约延迟命令 + 监测打断"做成每 tick 一次批量检查，而不是每个决策单独轮询。
- **多机堆引擎**：最直接的扩容手段（双机桥接曾把产出推到 ~2,760 局/h），但要注意 learner 侧消费能力——产得太快而消费不掉，产出会被丢弃。

### 7.4 一句话结论

事件驱动把"何时决策"和"何时动手"都交给了模型，表达能力更强；代价是**训练循环必须逐 tick 推进引擎以捕获稀疏事件，并为延迟命令做排程**。所以在自博弈阶段，**决定吞吐的是引擎推进速度，而不是 GPU 算力**——能不能训得动，取决于引擎侧（原生步进、多对局、异步重叠、多机扩容），而不是换更大的模型。
