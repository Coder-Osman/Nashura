# FirstLight CR：从开源离线引擎到专精智能体

> **从回放到智能体，从自博弈到竞技场。**
>
> 一个面向 Clash Royale 研究的离线训练项目：使用真实游戏逻辑作为黑盒环境，结合模仿学习、强化学习和大规模自博弈，训练能够理解局面、记忆对手信息并形成专属打法的 AI。

## 项目从哪里开始？

项目基于开源仓库 [FirstLight_CR](https://gitlab.com/firstlight3/FirstLight_CR)。它提供了完整的研究基础设施：

- 真实游戏逻辑驱动的离线战斗环境
- Android ARM64 引擎与 C/C++ probe 接口
- 无渲染 headless 模式和原生逻辑逐 tick 推进
- 结构化公平观测、动作接口和回放重建
- 模仿学习（IL）与 PPO 自博弈训练代码
- resident 多对局、批量传输和分布式训练框架

项目不连接 Supercell 官方服务器，不操作官方账号，也不分发第三方游戏二进制。用户在本地提供匹配版本的 APK 和资源，所有训练均在隔离的离线环境中完成。

## 我们做了什么改动？

### 1. 先把真实引擎变成可训练环境

原始游戏引擎不是为强化学习设计的。我们保留它的真实战斗逻辑，只在外围增加训练接口：

```text
Python reset / step
        ↓
原生 headless GameState
        ↓
结构化观测、动作收据、战斗事件
        ↓
策略网络与训练器
```

每个 Tick 代表 50ms。策略每 5 Tick 做一次决策，既保留真实战斗节奏，又避免每个渲染帧都产生训练开销。

### 2. ARM64 引擎在 x86 主机上的离线运行

训练服务器是 x86_64，但 Android 35 的 x86_64 模拟器包含 ARM64 转译能力。我们验证了真实 ARM64 引擎可以在 KVM 加速的 x86 模拟器中运行，因此无需重写游戏内部逻辑，也能把原生战斗引擎作为黑盒环境使用。

### 3. 从 JSON 单场通信升级为 resident 批量数据平面

最初的方式是一个进程服务一场对局，每个决策周期都要进行多次 JSON 往返。我们启用了上游已经实现、但此前没有使用的 resident 路径：

- 一个引擎进程内保留多个独立 GameStateManager
- 每个 resident slot 是一场独立对局
- 一条二进制 `batch-v1` 请求同时推进多个 slot
- 观测随 step 响应一起返回，省去独立 observe 请求
- 训练捕获使用紧凑 CRTF 二进制格式，而不是完整 JSON
- 连接保持常驻，避免每个 Tick 重建 TCP 会话

在我们的机器上，24 个引擎 × 8 个 slot 可以同时运行 192 场对局；相比早期的单场 worker 架构，聚合吞吐从约 492 tick/s 提升到约 2,190–2,250 tick/s。

### 4. 探针增量游标

原始观测会重复传输事件环的整个保留窗口。我们为 phase、combat、remaining、visibility 四类事件增加增量游标：

- 只传输上次读取之后的新事件
- 观测传输量减少约 97.7%
- 在多实例训练中显著降低 TCP、JSON 和 Python 解析压力

### 5. GPU 推理与 resident worker 分离

引擎 worker 负责：

- 推进真实引擎
- 读取 CRTF
- 生成模型输入
- 提交动作

策略网络放在 GPU 上，使用 recurrent actor-critic 模型。一次模型推理可以覆盖同一批 resident 对局的多个 actor。现阶段使用批量张量输入，后续继续推进中央推理服务器和 CUDA Graph。

### 6. 对手信息保持公平，同时增加可学习的记牌特征

模型不会直接看到对手的真实私有手牌和精确圣水。它能看到的仍然是公开信息：

- 对手已经公开打出的牌
- 根据公开牌序推断的循环状态
- 对手圣水的上下界和不确定度
- 对手当前可能在手中的牌、可能的下一张牌（由公共 tracker 推导）

新增的两个模型特征是：

- `public_in_hand_estimate`
- `public_next_draw_estimate`

这不是上帝视角，而是把人类玩家可以通过记牌得到的结论显式提供给模型，避免 LSTM 把大量容量浪费在重新学习牌组循环算术上。

同时，卡牌 token 在模型中使用无位置编码的注意力集合结构：交换卡牌行不会改变策略和值输出；中间 token 序列只发生对应的行置换。

### 7. 旧模型迁移与蒸馏

新增卡牌特征后，旧模型的输入维度从 16 列增加到 18 列。我们实现了受限迁移：

- 旧权重前 16 列逐位复制
- 新增两列权重零初始化
- 其他模型结构、catalog 或 checkpoint contract 不匹配时拒绝加载
- 旧模型可以作为新输入 schema 的安全起点

随后使用旧 General 模型生成专家轨迹，通过行为克隆（BC/IL）得到新 schema 的学生模型。实测收集了 192 场对局、约 463,100 个 owner decision frames；学生 checkpoint 已成功产出（step-574）。

### 8. 训练记录格式扁平化

早期 rollout 每帧保存大量嵌套 Python 对象，trainer 读取单条记录约需 1.3 秒。我们改成整局扁平保存：

- 一局观测沿时间维度预先拼接
- 动作、奖励、value、log-prob 和 mask 使用连续张量保存
- trainer 读取后通过 `narrow_batch` 切回时间帧
- 兼容旧格式
- 实测单条加载从约 1.29 秒降到约 0.016 秒，约 80 倍提升
- 文件体积约减少 30%

同时增加原子文件发布，避免 trainer 在 worker 尚未写完文件时读到半成品。

## 当前模型与训练路径

当前训练采用三阶段路线：

```text
旧 General 模型
      ↓
新公平观测特征 + checkpoint 迁移
      ↓
行为克隆蒸馏学生
      ↓
三卡组专精 PPO 联盟训练
      ↓
单倍圣水稳定性验证
      ↓
双倍/三倍圣水迁移与完整对局训练
```

## 正在进行的专精训练

我们将训练三个独立策略，而不是让一个模型同时记住三种完全不同的打法：

### 速猪

```text
Hog Rider / Ice Golem / Musketeer / Skeletons
Fireball / Log / Cannon / Ice Spirit
```

目标：快速循环、桥头施压、低费防守转反击。

### 暗巫精锐石头人

```text
Golem / Dark Witch / Elite Barbarians / Baby Dragon
Mega Minion / Lightning / Log / Tombstone
```

目标：沉底积累、重型推进、利用防守剩余单位形成反攻。

### 皮卡锤

```text
P.E.K.K.A / Battle Ram / Bandit / Royal Ghost
Electro Wizard / Poison / Zap / Minions
```

目标：桥头压制、防守赚费、P.E.K.K.A 防反和法术价值最大化。

每个卡组对应一个 specialist policy。三个策略通过有序循环赛互相博弈：速猪↔石头人、速猪↔皮卡锤、石头人↔皮卡锤，并交换双方先后顺序。

## 奖励设计：从“只看输赢”走向分段局面学习

仅使用最终胜负会造成严重信用分配问题：一局有约 1,200 个决策点，但最终只有一个 ±1 结果。我们正在实现的奖励方案把对局按场上单位和建筑都清空的时刻划分为多个局面片段。

### 第一阶段：单倍圣水

单倍圣水阶段持续到 2x 圣水开始前。每个片段重点衡量：

- 我方对敌方公主塔造成的血量损失
- 敌方对我方公主塔造成的血量损失
- 双方圣水差
- 手牌循环差
- 已公开牌和可推断牌序

基础片段奖励为：

```text
r_segment = k × 净公主塔血量差
          + λ × [γ^T × V(s_end) − V(s_start)]
```

其中：

- `k` 把公主塔血量变化归一化到塔分尺度
- `T` 是片段持续的 Tick 数
- `V(s)` 是 critic 对局面未来收益的估计
- `γ^T` 与片段持续时间对应，避免边界价值系统性偏移
- 价值项在奖励中使用 detached 数值，避免策略通过操纵 critic 刷奖励

按照当前设计，王塔血量不纳入单倍圣水片段的直接血量差奖励；王塔与皇冠奖励留到后续完整对局阶段重新加入。

### 第二阶段：价值函数辅助

价值函数回答的是：

> 从当前局面开始，按照当前策略继续打下去，未来预计还能获得多少净收益？

它不是额外的规则，而是 actor-critic 模型已有的 critic head。训练方式是标准 PPO：

```text
真实 rollout 奖励
      ↓
折扣累计回报 G_t
      ↓
critic 学习 V(s_t) ≈ G_t
      ↓
优势 A_t = G_t − V(s_t)
      ↓
PPO 更新策略
```

在分段奖励中，价值函数用于修正“这一波结束时双方并不平费”的情况。例如，一方用较少圣水守住进攻，虽然本段塔血变化接近 0，但它可能把下一局面变成明显优势。血量差负责记录已发生的结果，价值差负责估计局面未来质量。

## 训练基础设施

当前正式联盟配置：

- 24 个引擎
- 每引擎 6 个 resident slot
- 最多 144 场并发对局
- 三个并行 trainer，每个策略一个 trainer
- 8 张 GPU，其中 3 张用于策略更新，其他 GPU 承担推理与数据任务
- 1x 对局上限为 2x 圣水开始前
- rollout 记录采用扁平张量格式，并使用原子发布
- trainer 消费后清理 on-policy 记录，限制磁盘增长

曾经验证过的更高并发配置是 24 引擎 × 8 slot = 192 场，但在扁平记录格式之前，trainer 消费速度跟不上；完成扁平化后才具备继续提高并发的基础。

## 接下来怎么训练？

### 阶段 A：三策略安全起点

从蒸馏学生 checkpoint 出发，三套卡组各复制一份模型：

- 保留旧 General 的通用决策能力
- 在新 18 列输入 schema 下继续训练
- 使用单倍圣水、分段血量奖励
- 保留圣水溢出惩罚，防止“憋费不打”
- 先不用过强的卡组专属启发式奖励

### 阶段 B：同步联盟共训

三个 specialist 同时更新：

- 每套卡组都与另外两套卡组交手
- 每个有序对局方向都被采样
- 每个策略独立保存 checkpoint 和 optimizer 状态
- 训练阶段热加载最新策略
- 记录策略对策略的净公主塔血量差矩阵

### 阶段 C：专精能力评估

每隔固定更新步数评估：

- 对每一套对手卡组的净公主塔血量差
- 速猪的循环和施压效率
- 石头人的推进与防守转反攻效率
- 皮卡锤的防守赚费和桥头双推效率
- 圣水溢出、被动等待、无效动作和动作拒绝率
- 三策略之间是否出现某一策略垄断或互相退化

### 阶段 D：迁移到双倍与完整对局

单倍圣水阶段稳定后：

1. 以单倍模型作为初始化
2. 恢复 2x/3x 圣水阶段
3. 重新加入皇冠和破塔奖励
4. 降低分段血量奖励权重
5. 评估模型是否会把单倍节奏错误地延续到双倍圣水

## 我们如何判断训练成功？

训练成功不等于 checkpoint 文件更新，也不等于某一局偶然获胜。我们会同时看：

- 净公主塔血量差是否持续改善
- 各类 matchup 是否都能保持合理表现
- 非 WAIT 动作是否稳定增加且合法
- 圣水是否有效利用而不是持续溢出
- 策略是否学会本卡组的典型节奏
- held-out 对手是否仍保持泛化能力
- 是否出现奖励黑客，例如只用法术磨血、无意义换血或长期互蹲

## 项目当前定位

FirstLight CR 不是简单地给一个模型喂更多对局，而是在搭建一条可验证的训练流水线：

```text
真实离线战斗逻辑
        +
公平可审计的观测
        +
高吞吐 resident 批量环境
        +
旧模型安全迁移与蒸馏
        +
局面级奖励与价值估计
        +
三卡组同步联盟训练
        ↓
可解释、可评估、可持续迭代的 Clash Royale 智能体
```

项目的下一步不是盲目增加训练时长，而是对奖励定义、局面切分、价值估计和专精能力进行对照实验，确认模型真正学到的是有效的战斗策略，而不是利用奖励函数的漏洞。
