# 采集段与原生引擎审查

本轮针对用户截图中的“采集与汇总”部分。只读取运行记录、代码和 Android 进程映射，另在闲置 cuda:1 上对历史观测做推理基准；未改动采集或引擎实现，未占用评估端口。

## 当前基线与长尾

截图的第 172–188 轮平均 160.7 秒属于常驻采集启用前。新增统计覆盖第 192–201 轮的 1,080 局；去掉 192 冷启动轮后，193–201 的采集与汇总平均 **110.19 秒/轮**，范围 **82.62–132.44 秒**。不同轮次的 seed、局长不同，该差值不是同场景 A/B 加速比。

|---|---:|---:|---:|---|
| 193 | 132.44 | 42.30 | 123.76 | .37 |
| 194 | 131.26 | 40.71 | 122.61 | .41 |
| 195 | 101.86 | 39.69 | 95.24 | .34 |
| 196 | 97.77 | 36.44 | 91.23 | .34 |

热轮的总采集时间通常比最长局多约 6.5–8.7 秒，包含约 5.6 秒推理文件导出、分发/换权重、reset、写盘与回传等。平均局约 40.5 秒，但同批所有 108 局结束才更新，主要尾部来自长局，慢机并不固定。

各主机累计耗时/累计局长约 13.83–14.29 ms/tick；不能把所有慢局简单归因于某一台机器。这里按 tick 归一化也没有控制场景中实体数量、卡牌动作数量等复杂度。

## 一局平均耗时拆分

| 环节 | 秒/局 | 解释 |
|---|---:|---|
| 环境 step 合计 | **29.62** | 下两项包含在里面 |
| 其中：channel 总计 | 15.82 | receive 14.61 秒，decode 1.20 秒，其余少量发送等 |
| 其中：channel 之外的环境工作 | 约 13.79 | 由嵌套计时相减；包含绑定/事件/观测/mask/协调等，不全是观测构造 |
| 模型推理 | **10.05** | encode、动作头与采样 |
| tensorizer/合法动作特征 | 0.81 | 推理前准备 |
| 单局总计 | **40.54** | 还有少量其他工作 |

引擎先回复批次头，再推进并生成 payload。因此 receive 包含引擎计算、观测采集、序列化和传输等待，不能称为“14.6 秒网络瓶颈”。每局平均返回 **54.75 MB / 223 批**。

计时还有一个小范围差异：channel profile 包含会话开始后的一次 1 tick priming，而 rollout 主循环计时在 priming 后开始。因此 13.79 秒只能作为差分近似；新增分段计时应统一起止边界。

## 优先级 1：单机共享 GPU 推理

当前每个端口一个 CPU policy，生产数据约 266–292 ms/有效决策。实测同一个第 191 轮模型和 64 条真实历史观测，包含输入打包、传设备、encode、动作采样、离散动作及 log-prob 回 CPU：

| 路径 | 64 条总耗时 | 平均每条 |
|---|---:|---:|
| CPU，batch 1 | 16.005 秒 | **250.07 ms** |
| GPU，batch 1 | 3.054 秒 | **47.72 ms** |
| GPU，batch 8 | 0.410 秒 | **6.40 ms** |
| GPU，batch 16 | 0.217 秒 | **3.38 ms** |
| GPU，batch 32 | 0.123 秒 | **1.92 ms** |

这是小样本离线吞吐基准，每种一次计时，已做初始 warmup；没有加入进程间通信和排队，也没有宣称 batch 32 的 1.92 ms 是单次请求延迟。GPU batch 8 整批处理约 51 ms；稀疏请求应及时单条执行，不能等凑满导致长局尾部停顿。

建议每台有 GPU 的采集机设置一个模型服务，18/24 个环境把 ready observation 发过去，按相同 checkpoint 小批合并。设短等待上限，例如先以 1–3 ms 作为待调参数，batch 上限先测 8/16；保持每局 RNG 规则，响应绑定请求、权重身份、mask、动作及行为 log-prob。

只需共享推理，环境继续独立推进，不增加神经记忆。最长局的模型推理约 17–29 秒，先减少这一部分有机会直接缩短轮次尾部；离线吞吐提升不能原样换算成整个采集段倍速。

## 优先级 2：Python 环境按需构造观测

约 **85.18%** 的推进步骤没有触发 event/wake 决策，但 `BattleEnvV1.step` 仍执行完整 `observe_dual`：实体、塔、双方玩家和合法 mask 等。下一次循环又可能只是 WAIT。

建议拆分：

1. 每次推进保留事件消费、tracker、计划执行、奖励与终局状态更新。
2. 只有策略决策或计划执行真正需要时，再物化对应玩家的完整观测和 placement mask。
3. 普通 WAIT 使用轻量校验；保留等待窗口与合法性检查。现有 mask 缓存继续使用，先测命中率，避免重复实现已有缓存。

当前约 13.79 秒是整个 channel 外环境工作的范围，不是已证明可以全省掉的时间。下一步要加 `_atomic_observation_pair/bind_rich_telemetry`、各类事件消费、`_derive_events`、`observe_dual`、`action_mask` 的独立计时，再给出具体节省量。

特别注意：减少模型观测构造，不等于跳过 native 事件采集。有些 remaining-runtime 的状态核对发生在 capture 路径内，需保持语义。保留 30 tick 上限；本次没有建议调大 tick 来掩盖开销。

## 引擎侧值得做的具体优化

### A. 同一帧只建立一次场景索引

生产源码 `build_atomic_observation_json_locked` 依次生成 ordinary 和 rich 两份观测，重复走同一个世界对象列表。rich 中 `resolve_bounded_entity_reference` 又按 pointer 查找对象，再由 `native_object_id_is_unique_in_vector` 扫描 ID 唯一性；目标、弹道源/目标、效果来源都会用到类似查找。

建议在一次固定 generation/stateEpoch/tick 的 capture 内建立 pointer→slot/identity 和 native ID 索引，集中做唯一性验证；ordinary、rich、目标引用和效果引用复用。索引只在当前 capture 有效，不跨 tick 保留裸指针。可以减少重复扫描，尤其值得在实体密集的长局上测量；尚未取得该部分独立耗时，不能声称已达到某个倍速。

### B. 精简重复的静态说明，再测无损压缩

生产 rich 头部的格式字符串约 **17,994 字节**，包含大量固定 provenance/source/validation 文本。按平均 223 批估算约 4 MB/局，约占总响应的 7%；它不是全部流量来源。

这些静态说明可以按协议版本/契约 hash 在握手时校验并缓存，帧里保留身份、动态状态和必要完整性标记。动态字段仍需验证。

现有引擎已经支持 `zlib-json`，这是适合先做真实对局 A/B 的低改动候选：字段不变，但会增加原生压缩及 Python 解压成本。应比较整体局耗时以及 step/capture/serialize/compress/send，不能只比较压缩率。当前没有执行 live zlib A/B，评估占用现有端口。

### C. 当前 compact 路径不是完整 JSON 的等价替换

`training_capture.py` 构造的 snapshot 把 `visibility_runtime`、`remaining_runtime` 置为 `None`；原生 compact writer 将 phase 事件数写为 0，仅保留部分状态。这与当前完整契约的信息路径有差异。

因此先补齐并验证字段、事件连续性和 tensorizer 输出，再考虑训练专用二进制协议。不要为了体积直接打开现有 compact 开关。

### D. 先拆出真正的引擎 tick 成本

`resident_step_bound_until` 是逐 tick 直接执行游戏 step，检查公开部署和终局后停止，循环中没有固定 sleep。长连接、TCP_NODELAY、响应 scratch buffer 复用都已经存在。

当前计时没有区分 `libg step`、普通采集、rich 采集/JSON、压缩、send，建议分别记录 ns、tick 数、对象数和 payload 字节数。优先以原生累计计数器回传汇总，避免每 tick 打日志反而拖慢。

运行环境也已确认：x86 Android AVD 内运行 ARM64 的 `libg.so` 与 `libcrprobe.so`，同一引擎进程映射中存在 `libndk_translation.so`。减少重复格式化和扫描也能减少桥接执行的工作；桥接本身的实际耗时占比尚未测得。迁移到 ARM 平台属于较大的基础设施实验，优先级低于上述代码改进。

## 已有优化与版本差异

这次专门比对了本地与实际运行快照：生产 combat、phase、visibility、remaining 的 JSON 发送已使用增量 cursor，本地部分源码仍发完整保留窗口。不要把本地旧逻辑误认成线上瓶颈，也不要把本地 probe 整份覆盖上去。

Python collector 常驻、窗口未就绪跳过 forward、纯推理权重、每机批量回传都已实现。传输层重复 JSON 校验在 factory 中也已关闭，BattleEnv 的 typed 校验仍保留。地址可读性检查已有缓存。新增优化应基于这些已存在的改进继续推进。

## 建议顺序与验收

先做单机共享 GPU 推理试点，同时补齐环境/引擎分段计时；之后做按需观测与当前 capture 的场景索引复用。zlib-json 可以在空闲测试端口作为独立 A/B，不与其他修改混在同一轮比较。

验收至少包含：完整终局、事件无缺口、公开 tracker 与 mask 对齐、行为概率重放通过、模型版本一致、固定种子下新采样协议可复现，以及满载 108 局的整轮耗时/尾部耗时。保留长局，不能用丢弃慢局来获得表面加速。
