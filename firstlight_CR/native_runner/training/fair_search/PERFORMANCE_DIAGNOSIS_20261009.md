# FAIR 后段根耗时增长诊断

## 运行范围

保持 `.34` 原诊断局和 `.37` 优化版完整局运行，不热更新源码或读取实际比赛隐藏状态。诊断在 `.37` 30049 独占引擎上执行，使用已存档的允许信息根玩家 1、tick 575，冻结 1755 checkpoint、FP32、同一独立 belief 采样 seed `3401193736`。该根完整信息 SHA256 为 `7a5550e78932555956675ee32bce39565b9bba24e1912b9f8f588314355142e3`。

## 已观察趋势

优化版完整局第 1–8、9–16、17–24、25–32 根搜索耗时中位数依次为 125.75、160.42、383.13、708.48 秒；tick 1356 两根分别 1783.50、2249.16 秒。这些根的游戏状态、搜索动作和推进量不同，不作为受控倍率。

检查时优化版没有生成重放失败诊断目录，进程仍有 CPU 工作，可用内存约 70GB，间隔换页采样为零；一次 GPU 利用率采样为零。这些采样排除了当时明显的内存压力，但不足以表示整个运行期间的负载情况。

## 定位结果

新 FAIR 入口实例化普通 `NativeClashEnv`；每个逐 tick 推进由 `BattleEnvV1._advance_headless` 执行 `step` 后再 `observe-atomic`，全 JSON 捕获。既有 PUCT 路径的 resident-hybrid、compact capture 和原子 step 接口没有在该入口接入。

native phase 遥测导出以 `retained_oldest` 为 `transmitFromSequence`，发送整个保留窗口。Python `_validate_phase_runtime` 虽接收 `minimum_sequence`，目前只核查游标范围和缺口，随后仍遍历全部 `events`。rich adapter 可跳过部分已消费事件，但前一层传输、JSON 解码和字段校验成本已发生。combat 校验也反复处理保留历史。

同一信念根只提交 WAIT，逐 tick 推进 200 次，在恢复后重复两遍。两个分支耗时 107.57、108.35 秒（开启 cProfile，绝对时间有 profiler 开销）。第一遍调用栈累计：

| 路径 | 累计秒 | 对分支墙钟比例 |
|---|---:|---:|
| 原子观测与 rich merge | 100.40 | 93.3% |
| 原子结果校验 | 50.39 | 46.8% |
| 其中 phase 事件校验 | 37.49 | 34.8% |
| 请求与响应读取，含 native 捕获等待 | 43.37 | 40.3% |
| rich merge | 12.02 | 11.2% |
| 单独 step 请求 | 5.41 | 5.0% |

各行有包含关系，比例不可相加。请求耗时含引擎捕获、序列化和等待，不等同于网络延迟或物理模拟时间。

第一遍 tick 580→600 的 20 tick 约 3.44 秒，tick 680→700 同样 20 tick 约 12.39 秒。对应 phase 保留事件 68→297 与 931→1171；对象数从 17 降至 13，因此该段增长不能仅用场上单位数解释。第二遍从同一恢复根重复得到同样事件数量及接近的区间耗时。

## 无 profiler 固定状态对照

再次重建相同兼容根，WAIT 推进 130 tick 至 tick 705。保存 native snapshot 与 state digest，先做 20 次不推进时间的原子观测，再恢复同一 snapshot、校验物理 state digest 相等后，重复 20 次原子观测。两侧都是 13 个对象。

| 测量 | 保留历史 | 恢复后的新日志窗口 |
|---|---:|---:|
| phase 记录 | 1231 | 6 |
| combat 记录 | 76 | 0 |
| remaining 记录 | 48 | 0 |
| 20 次原子观测总耗时（秒） | 7.08858 | 0.50596 |
| 请求、响应读取与 JSON 解码（秒） | 5.16565 | 0.30290 |
| 返回后 Python 校验（秒） | 1.92293 | 0.20306 |

相同物理状态的捕获成本约相差 **14.01 倍**，支持历史窗口反复序列化、传输及校验是主要性能问题。恢复同时改变遥测代次和缓存，不能把差异全部归于单个 phase 函数；没有模拟时间推进，排除了额外游戏 tick 的物理计算。恢复后六个 phase 记录为根 tick 测量基准。此实验只用于诊断，训练运行没有用清空日志替代正常事件消费。

同一无 profiler 分支的前段 20 tick（580→600）约 2.16 秒，后段 20 tick（680→700）约 7.20 秒，再次验证增长趋势。单次受控对照未测完整 32 次搜索或整局收益。

根耗时由重建、32 次模拟的推进量、每 tick 捕获成本、决策与推理及恢复共同组成。既有固定根测量中，tick 764 为 1059 次推进，tick 575 的长尾根为 5697 次，后者即使零拒绝也需约 1703 秒。32 次预算固定不代表推进数量固定；事件稀疏的分支会更接近 10 秒游戏时间上限。对 tick 1356 完整局根尚未注入逐根计数，不能为该根分摊精确占比。

## 优化顺序

1. 接入已验证的 resident/compact 原子 capture 路径，同时保持 native 每 tick 推进、动作执行收据和严格 FAIR 校验。
2. 通过代次、完整窗口头和消费游标只发送新事件；先保留完整校验，验证 gap、overflow、restore 及 phase 测量边界。不要以全局跳过校验掩盖成本。
3. 对已验证的历史仅做增量字段校验，保持完整 header、序号和新事件检查；缓存绑定 native generation/stateEpoch，恢复或更新即失效。
4. 完整 root 审计通过后评估重复分支前缀快照复用，并单独测量采样状态和 RNG 等价性。

不通过增加 tick 跨度、减少 32 次模拟或读取实际比赛隐藏状态提升速度。GPU 合批主要解决推理利用率，当前诊断显示应先处理遥测路径。

原始证据位于 `_spec_work/evidence/fair-search-20261009/tick-profile/`、`tick-profile.log`、`fixed-state-profile/` 与 `fixed-state-profile.log`。诊断脚本 `profile_tick_cost.py` 保存剖析参数、请求计数和物理 digest 校验。两台原有训练验证进程未修改。

## 已实施的捕获路径修复

FAIR 新入口已接入独占 slot 0 的 `ResidentBatchChannelV1` 压缩训练捕获，正式推进逐 native tick，同次响应取得 ordinary 与严格解码的 typed rich snapshot，同 tick 后续观测直接复用。初始化预热保留原控制语义，reset 后启用；控制及快照请求关闭 batch、清除缓存并校验独占 slot。显式 `--transport json` 保留旧路径作对照。

本次实现优化顺序的第一项，仍传输完整事件窗口；没有把诊断中的清空日志方案用于运行，也没有实现 native delta 协议。135 项相关测试通过。

固定长尾根 compact 版本完整 32 次搜索为 162.94211 秒，与已存档 JSON 版本 1703.43475 秒对照约 10.45 倍。双方推进数均为 5697，全部 77 个信息帧、分支轨迹、访问分布与选中动作一致。基线来自此前记录，尚不属于本轮交替重复测量；根收益也不等于完整对局或训练倍率。详细证据与后续交替测量见 `VALIDATION_20261009.md`。

固定 tick 764 的三组有效交替测量已完成：根中位数 147.42999 → 61.51560 秒，约 **2.40 倍**；每侧均推进 1059 次，全部 86 个信息帧与搜索输出一致。逐 tick advance 累计中位数 108.59291 → 19.36319 秒，说明捕获路径优化确实减少推进成本，但根的其他工作仍限制总倍率。详细记录保留 resident 模式切换失败，并说明第一对共用端口、后两对使用固定模式的独占端口；没有将失败或未完成试验计入倍率。
