# 本机 CR 工作台

双击项目根目录的 **启动视频工作台.command**，浏览器自动打开 <http://127.0.0.1:8765>。首次同步历史权重约需一至两分钟，之后使用本机 SQLite 索引和远端 SHA 元数据缓存。

顶部可切换“对局视频”和“私服对战”（`/live/`）。两个页面共用同一份权重目录、权重 ID、SSH 配置和刷新任务，后台启动时及每五分钟同步一次。私服对战仅在开局时下载选中的权重，SHA 校验后缓存到 `artifacts/render-web/weights/`；同一 SHA 复用同一文件，并发请求也只下载一次。视频生成继续使用远端原始归档。私服对战日志保存在 `artifacts/live-web/`，其启动器也复用这个统一服务。详细操作及实时观测限制见 `live_web/README.md`。

停止工作台服务也会停止私服 AI 接管，保留游戏窗口和进行中的游戏对局。

1. 选择“同一权重”或“两个权重对战”。默认是当前训练最新完整权重、石头人镜像。

权重下拉框区分“正式训练”和“塔血实验 β=1 · 1553 起点”。正式训练最新为1553；独立实验从1553继续至1753，选项注明实验更新进度和SHA，支持与正式权重对战。实验目录从`.37`归档读取，仅收录连续通过更新回读、写入完成记录的权重；采集中或尚未验收的更新不会进入列表。顶部提示分别显示两个类别的最新轮次，随工作台原有五分钟刷新更新。无需复制或替换正式训练权重。

另有“近静场结算 β=1/3 · 1553 起点”分类，从`.37`的`/data/firstlight/settlement-nearquiet-formal1553-200r-20260923/training`读取。本分支同样从1553更新200次至1753，与旧塔血实验通过独立分类、run_id和SHA区分；216/324容量测试的临时权重不入目录。索引核验首轮验收、连续父权重、奖励配置、优化器恢复及更新回读，随后每五分钟同步新增完整轮次。视频和私服页面共用同一身份；视频跨磁盘固定权重时会复制并再次核验SHA。
服务器另有从塔血实验 RL 1753 接续的 `rl108-beta015-overflow003-20260928` 分支。该分支采用 v6 奖励（塔血 β=0.15、溢费每点 0.003），当前已收录 RL 1754、1755；工作台单独标记为“正式训练 · 1753 续训（塔血 β=0.15）”，不把它改写成旧正式 RL 1553 的直接延续。
2. 分别选择上下方卡组，可用石头人、巨人、野猪、皇家巨人、卫队猪五套混合训练牌表，也保留皮卡和天狗。卡组选择下显示完整牌表；同一权重也可使用不同卡组，交换按钮同时交换权重与卡组。171 原模型与同轮次残差迁移模型会分别显示。
3. 默认随机生成 32 位种子；需要复现时展开“指定种子”输入整数。点击“生成对局视频”，任务参数、双方 SHA 和八张卡的有序牌表在提交时固定。
4. 在“当前任务”查看进度和耗时，在“视频历史”播放或下载。核验详情及未完成任务默认折叠，展开后可查看记录、失败原因或重试。

导出的 MP4 只保留完整对局画面。轮次、种子和权重等信息可在网页详情及核验记录中查看。

关闭网页不会停止任务。双击 **停止视频工作台.command** 会取消当前任务并收尾，然后退出服务；尚未开始的排队任务保留，下次启动继续。录制期间取消可能需要等待约三分钟，让 Android `screenrecord` 自然写完文件。成功、失败或取消后，专用模拟器会关闭。

## 配置与依赖

当前 Mac 使用 `/opt/anaconda3/bin/python`，可通过 `CR_RENDER_PYTHON` 指定其他 Python 3.11+。网页没有 Node 构建步骤。独立依赖清单为 `requirements-render-web.txt`；在需要的新环境中运行：

```sh
python -m pip install -r "requirements-render-web.txt"
python -m render_web start
python -m render_web stop
```

将 `.env.render-web.example` 复制为本机私有 `.env.render-web`。配置仅由后台读取，不发送到浏览器。优先使用现有 SSH 密钥或 agent；密码配置也仅留在权限为 600 的本机文件。SSH 严格验证已知主机密钥。`.37` 到 `.34` 需要既有免密 SSH 和已核实的 known_hosts。

默认仅监听 `127.0.0.1:8765`。`.34` 提供完整训练记录，`.37` 核实归档权重并生成轨迹。仅支持当前冻结运行时可加载的 V2/V3 无状态权重，拒绝旧语义；不做自动迁移。不同残差结构可对战，但输入、动作、event 与 backbone 配置必须一致。

远端使用独立 `firstlight-render-web / emulator-5590 / 27889`，本机使用 `astral-api30 / emulator-5554 / 26789`。远端5580由近静场训练审计实例使用，工作台改用5590/5591控制台及ADB端口，避免重叠。资源已有其他使用者时任务等待（也检查同一 AVD 在其他端口的占用），不结束其他会话。全流程复用已有本机 SDK、离线 APK 和 ffmpeg。

人机对战复用已安装完整游戏的 `astral-api30`，以 `emulator-5564 / 27789` 启动。它与视频任务共用 `worker.lock` 串行运行；同一时刻只有一个任务占用此 AVD，不安装新 APK。

当前 `.37` 已为工作台单独配置 AVD。需要在相同部署目录重新准备时，运行 `python -m render_web bootstrap`：等待模板 `firstlight-video251` 完全停止后，独立复制配置、用户数据与密钥镜像，并保留 QEMU 版本标记以避免首次启动重建数据盘，保留已验证的 APK 和 15.535.86 更新资源；复制后再次检查模板已停止，整个过程不修改模板。初始化需要远端至少 8 GB 空闲；本工具先前创建的目标会保留在 `bootstrap-backups`。应用运行期间的原生核验可能较慢，后台保留单次请求等待哈希计算，避免重复请求积压。

## 数据与生命周期

所有本机产物位于 `artifacts/render-web/`：

- `workbench.sqlite3`：索引、固定参数、队列、阶段、worker 归属和核验结果。
- `server.log`：服务日志。`server.lock` 与 `worker.lock` 防止重复服务和并发模拟器作业。
- `jobs/<任务 ID>/`：动作轨迹、完整发牌、原生回执、双方身份、渲染日志、核验 JSON、原始录像和最终 `video.mp4`。

远端产物位于配置的 `remote_root/jobs/<任务 ID>/`，任务权重以不可变 SHA 归档的硬链接固定；生成时再次验证完整 SHA。冻结的 `event-scheduling.v2` 运行时置于 `remote_root/runtimes/<运行时 SHA>/`，源码使用独立副本，每次使用前核验源码 manifest。生产代码不引用临时目录脚本。

五套混合卡组直接复用 `native_runner/training/mixed_decks.py` 的牌表。新任务的 `deck_cards` 贯穿远端生成、统计和导出记录，并与引擎配置及开场发牌核对；远端生成使用固定牌表，因此无需修改冻结运行时的旧卡组注册表。历史任务缺少此字段时仍使用原冻结注册表，重试保持原牌表及槽位顺序。

只有成功通过检查的任务会开放视频文件接口。视频保留到用户手动删除；删除任务会先清理对应远端目录，再清理本机目录，不删除训练归档。低于默认 2 GB 可用空间会拒绝新任务，也会在执行前再次检查；不会自动删除视频或训练文件。

网页刷新、断开不影响后台。SSH 断线后按原任务 ID 查询，不重新随机生成；持续离线超过三分钟会记录失败，资源清理在连接恢复后继续。HTTP 服务意外重启会接管仍存活的独立 worker；已经退出的 worker 会按 PID 和启动时间核对所属资源，清理后标记为“已中断”。重试使用原参数，优先复用已经完整校验的轨迹。清理未完成时队列等待。

本机启动超过 180 秒时会保存 `boot-status.jsonl` 和对应尝试的 `boot-diagnostics-N.json`（ADB 状态、系统属性、logcat），关闭已核对归属的模拟器后最多重试一次。录屏退出码保存在 `recording-exit.json`；非零退出码会保留在核验记录中，只有原始录像覆盖终局、全帧解码通过、发牌与出牌回执及胜方一致时才允许继续导出。原始录像核验为 `recording-validation.json`，最终视频仍须单独通过全帧解码。重试会重新核验并复用完整录像，核验失败则重新渲染，原失败任务及证据保留。

Mac 可用空间与 Android 内部 `/data` 分别检查。每次启动、录制收尾和中断恢复时，自动回收工作台的 `render-web-<任务 ID>.mp4` 临时录像：先确认录屏已结束，再核对本机副本的 SHA-256，通过 root 直接删除 `/data/media/0` 中的对应文件并检查删除结果，最后执行 `sync`，再关闭模拟器。本机缺少一致副本时先拉回 `guest-recording-archive/`，校验失败或本机空间不足则保留模拟器原件，下一次启动重试。游戏数据、更新资源、可复用的纹理缓存、其他录像以及本机视频历史保持保留。

启动期间低于 256 MiB 时先尝试上述清理，仍不足则保存诊断并停止；启动完成后和录屏前要求至少 600 MiB（180 秒、20 Mbps 录像加系统余量）。`guest-disk.json` 保存实际可用字节数，`guest-cleanup-<阶段>.json` 记录清理前后空间、文件 SHA、本机副本位置及失败原因。

录屏前及录制期间定期检查窗口焦点；系统崩溃或无响应弹窗遮挡画面时停止发布并保存 `visual-review.json`。人工画面检查标为失败的录像也不会在重试时复用，仍可复用其完整对局轨迹。

## 自动核验的范围

生成端必须到真实 `native_final_result`。回放前核对双方四张手牌和四张循环牌；必要时只重排本机 deck 槽位，保留原出牌坐标和执行 tick。逐条比对 owner、cardId、executeTick；要求全部回执成功，失败和待执行均为零，终局胜方一致。

录制可加速，导出恢复正常速度并裁去静止尾部，以原始画面尺寸输出完整对局。轮次、卡组、种子和 SHA 摘要保存在网页详情及核验记录中。最终文件为 H.264 / yuv420p / faststart，使用 ffmpeg 全帧解码后才发布。核验记录如实保留生成和渲染的终局 tick 差。自动校验并不等于人工观看；本次交付验收的画面抽查另记于 `artifacts/render-web/acceptance.md`。
